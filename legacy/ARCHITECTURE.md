# Lay Code 总体架构规划

**设计提案 · 2026-11-22**　面向独立开发者在本机代码库中的交互式工作。下文的技术选型、资源预算和发布门槛均为待验证的设计决定。

**建议采用单进程、单写者的 C++20 CLI。** 第一个发布版本要跑通“定位 → 修改 → 验证 → 中断后核账”。模型提供下一步提案，宿主掌握权限与执行顺序，SQLite 保存已提交的事实。架构的重心在两道提交边界：完整回复提交后才派发工具，外部动作结果提交后才让模型据此继续。

## 1. 从一次真实修改出发

假设用户说：“修复配置解析器读不了空文件的问题，只改解析器，跑对应测试。”模型最初并不知道解析器在哪里、工作树上有哪些未提交改动、测试能否运行。一次有价值的交付要回答三个问题：**改了什么，凭什么这样改，怎样知道它现在能工作。** 找到源码、观察失败、提交小范围修改、取得测试结果，构成这个任务的最短路径。若测试环境缺失，准确交代已改内容和缺失的证据，同样是有效终点。

由此推导四个职责。模型选择下一步。宿主决定这一步是否获准，并负责执行。工作区提供当前事实。会话记录保存当时看见和做过的事。四者有不同的可信度和生命周期，尤其要防止把模型写出的“测试通过”当成进程退出记录。

**首版形态**定为一个本地 CLI、一个工作区、一条线性会话、一个活动模型请求、串行工具调用。默认使用者在场。它应能解释代码、修改已有文本或创建源文件、运行用户认可的构建或测试，并在中断后交代进度。模型推理放在提供方，C++ 负责启动、流处理、文件、进程和持久化。建议以 Windows x64 本地 NTFS 为首个发布目标，Linux CI 用于尽早发现不可移植的假设。两者分别通过平台验收后才宣称功能可用。

Pi 值得借鉴的是用户可以看见工具在做什么，以及一套小工具能支撑完整的改码循环。它也提供树形会话、多个接入面和扩展系统。Lay Code 先解决线性会话中一次修改的因果关系。回到旧对话节点不会同时恢复磁盘上的文件，引入分支之前需要单独定义工作区语义。[Pi 作者的初版设计说明](https://mariozechner.at/posts/2025-11-30-pi-coding-agent/) · [Pi 的会话与扩展设计](https://pi.dev/)

## 2. 一个进程，三个必须守住的边界

```text
用户 ──意图、批准、取消──► 终端 CLI ◄──进度、差异、结果──┐
                             │                          │
                             ▼                          │
                       会话控制器（唯一写者）───────────┘
                       ├─ 上下文投影 → 模型适配器 ⇄ HTTPS/SSE
                       ├─ 工具准备 → 权限判定 → 原生文件操作或子进程
                       └─ 本机会话库（SQLite）
```

图中的箭头表示调用方向。完整回复、失败及工具观察值沿原路返回控制器。

1. **模型与宿主之间传提案。** 一段文字、一个完整的工具参数对象、一个得到授权的执行计划是三种东西。只有控制器能从前两者推进到第三者。
2. **工作区与会话之间传观察。** 同一文件可能在两轮对话间被编辑器改写。记录里保存读取时的版本，修改时重新验证。恢复会话只恢复知识和进度。
3. **持久状态与实时显示之间传通知。** 半句话也可以立即显示。只有通过协议检查并成功提交的回复才能进入下一轮上下文。显示器断开、渲染变慢或丢弃中间刷新，都不能改变一次工具是否被执行。

控制器拥有轮次状态、执行顺序和数据库写连接。网络和阻塞工具 I/O 在工作线程进行，交回带请求标识的值。取消走独立唤醒通道。首版一次只有一个活动操作，可复用一个 I/O 工作者。进程输出由平台实现同时排空两个管道。SQLite 事务期间不等用户、网络或子进程。CLI 只发用户意图，不直接动文件。依赖由入口组装，模型适配器和工具互不认识。目录边界先落实为编译依赖，无须为每个目录创建动态库。

## 3. Agent Loop 与停止条件

一次**任务**从用户提交意图开始，一**轮**包含一次模型回复及其产生的整批工具调用。模型自然结束发言只表示本轮交还控制权。宿主单独标记验证命令、退出状态和运行时最后一次已知编辑序号，让用户能判断证据覆盖到哪里。

| 当前状态 | 输入与提交条件 | 下一步 |
| --- | --- | --- |
| 等待输入 | 用户意图与选定的工作区、模型、能力范围已记录 | 构造请求，检查预算 |
| 等待模型 | 文本增量供显示。收到协议终止、支持的停止原因和完整内容块后，事务写入回复与有序调用清单 | 正常结束则交还用户。有调用则逐个准备 |
| 准备工具 | 校验工具名、参数与资源上限，解析真实目标，计算差异或命令预览 | 允许的读取直接派发，需要确认则等待，无效则记错误 |
| 等待确认 | 用户对本次目标、参数及版本作决定 | 拒绝产生可见结果。批准后复核前提并提交派发标记 |
| 执行工具 | 原生工具返回结构化结果，控制器按调用 ID 提交 | 成功则处理下一个。失败、拒绝或取消时将未开始项记为跳过 |
| 归并本批 | 每个调用都已有一个结果，顺序与原提案相同 | 完整回填，再发下一轮。若用户停止，停在可恢复边界 |
| 暂停或结束 | 上限、协议错误、未知副作用、用户停止、模型拒答或正常结束均有独立原因 | 输出最近差异与验证证据，等用户决定 |

**执行顺序。** 模型同批请求“编辑文件、运行测试”时，按原顺序逐个执行。编辑失败便跳过测试，避免拿旧文件的通过结果解释新修改。读操作并行可能节省延迟，也会引入排序、取消、快照一致性问题。等轨迹显示独立读批次是瓶颈再做。用户在执行时补充的话先排队，界面显示“待生效”。要立即改变方向可取消，未开始调用随即跳过。完整工具结果先回填，再加入新指令。

**停止策略。** 起始预算建议每项任务最多 24 次生成请求、64 次工具调用和 15 分钟活动时间，等待人工决定时暂停活动计时。重试占请求预算，进程另有超时。连续两次出现相同的调用参数、已知输入版本和同类错误时暂停并显示原因。拒绝决定绑定到本任务内同一动作，模型改写说明文字不能反复索要同一批准。Ctrl+C 停止下一次派发，取消当前网络传输或请求终止进程。命令已产生的改动保留并报告。

**示例轨迹。** 用户指定修解析器 → 搜索定位实现和既有测试 → 读取源码获得版本 v7 → 用户批准针对 v7 的四行差异 → 提交派发记录 → 应用编辑，返回 v8 → 用户批准运行对应测试 → 记录退出码、测试筛选条件与输出尾部 → 模型给出说明，CLI 附上工具记录。如果批准期间 v7 已变，返回“文件已更新”，展示新差异前先重读。如果测试程序缺失，界面显示“未能启动测试”，与断言失败及验证通过分别呈现。

终端将模型的自然语言和宿主的验证记录分开显示。记录列出实际程序、参数、退出码、执行后观察到的测试摘要及对应的工作区编辑序号。缺少可识别的测试器证据时，仅显示“命令退出 0”。后续编辑使旧验证标为“针对较早版本”；外部改动无法完整追踪时，界面保留时间和已知版本，避免把一次历史运行表述为当前整棵工作树均已验证。

## 4. 模型通信

首个真实适配器建议采用 **Anthropic Messages 的文本与客户端工具子集**。它有文档化的流结束事件、工具调用关联和停止原因，便于编写契约测试。具体模型 ID、上下文窗口、输出上限和协议版本在接入时固定并记录。首版只公布经过验证的组合。若首批用户使用其他供应商，可替换首个适配器。另备一个脚本化模型作为离线测试夹具，提供相同契约。[流式消息](https://platform.claude.com/docs/en/build-with-claude/streaming) · [工具调用约定](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

- **输入。** 适配器接收不可变请求视图，包含指令、选中的历史块、工具描述、模型参数与截止时间。凭据仅由传输端读取。每个请求绑定会话、轮次及尝试号，旧请求的迟到回调不得完成新请求。
- **接收。** libcurl 交付任意长度的字节片段。先按 SSE 规则分行、拼合多行数据并识别空行，再解 JSON，按块索引组装文字和工具参数。UTF-8 字符、CRLF 及 JSON 转义均可能跨回调。心跳可跳过。影响对话语义的未知内容停止本轮，可忽略的元数据只进入诊断。[SSE 解析规范](https://html.spec.whatwg.org/multipage/server-sent-events.html#event-stream-interpretation) · [提供方事件格式](https://platform.claude.com/docs/en/build-with-claude/streaming)
- **提交。** 终止事件、停止原因、块闭合、ID 唯一性与调用结构均须成立。输出达上限、异常 EOF、流内错误均不能触发工具，即使之前出现了看似完整的 JSON。全批参数在派发前完成结构与 schema 预检。若其中一项无效，则记录对应工具错误，其余项记为跳过。无法还原消息结构时整轮失败。同一回复中的调用在下一条用户消息中集中回填，按原 ID 配对。[停止原因](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons) · [多调用回填](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)
- **故障。** 分别控制连接、无数据等待及整体截止时间。从未提交的请求边界重试。429 遵守服务端等待提示，短暂网络错误和部分 5xx 采取带抖动退避，起始上限为两次自动重试。认证、无法修复的参数和协议错误直接报告。重发会产生新的生成结果，亦可能重复计费。已提交的助手回复由本地记录驱动后续动作。累计 token 用量按适配器的语义归并，缺失标为未知。[API 错误](https://platform.claude.com/docs/en/api/errors)
- **有界输入。** 给单事件、调用参数、块数和整条响应分别设上限。超限终止，不把截断的参数交给工具。原始 HTTP 日志默认关闭，错误记录只保留请求 ID、状态、阶段及筛选过的诊断。推理签名、服务端工具和多模态块留给将来的协议版本；要求这些能力的模型须先实现完整的往返测试。

## 5. 工具集合与执行契约

工具数由三个问题决定：能否在较小权限下发现事实，能否审阅变更，能否验证结果。首版用下列四项覆盖它们。能力描述、宿主参数验证和模型看到的 schema 源于同一份静态定义。授权与工具实现都使用解析后的同一份动作，避免预览与执行分岔。

| 工具 | 模型提供的输入 | 成功结果与约束 |
| --- | --- | --- |
| `read` | 相对路径、起始行、行数。对目录作单层列举 | 文件返回行号、内容、版本凭据及下一偏移。目录返回有界条目。报告编码不支持、二进制、截断和权限错误 |
| `search` | 相对目录、字面文本、可选文件名筛选、结果上限 | 返回路径、行号与短摘录。按需遍历，明确跳过目录、扫描上限与未覆盖范围。限制单文件大小、总字节数和耗时 |
| `edit` | 单文件、读取版本、唯一旧片段与新片段。新建时显式要求目标不存在 | 先生成差异，再复核目标。零匹配、多匹配、版本不符均返回冲突。成功返回前后版本。多文件任务可部分完成 |
| `run` | 可执行程序、参数数组、相对工作目录、超时 | 返回解析后的程序路径、退出／信号／超时状态、stdout 与 stderr 摘录、遗漏字节和用时。关闭交互式 stdin。用于用户批准的本机构建与测试 |

**读取与发送。** 初次会话让用户选定根目录、模型目的地和可读范围，明确获准的文件摘录会发送给该模型。目录枚举、搜索、读取、上下文装配共用同一套范围与排除规则。默认排除版本库内部、常见凭据文件和用户指定的私有目录。仓库文本、测试输出及项目说明保留来源，不能给自己扩大权限。敏感文件名无法穷举，目录选择与发送范围仍是实际授权边界。

用户可以把本任务的可写范围收紧到指定文件。在“只改解析器”的例子中，先读后定位，再在批准差异时把内置编辑限于该路径。项目内的说明文件可由用户选入上下文，其内容不能更换提供方、注入凭据或给命令自动放行。

**写入。** 对可编辑大小内的文件计算原始字节摘要，给模型一个短版本凭据，由宿主将其绑定到工作区、路径、文件标识和完整摘要。匹配层可展示统一换行，写入层须保留未改字节、BOM 和原有换行。混合换行无法无损映射时拒绝编辑。每个批准项绑定调用 ID、目标对象、前态和预期后态，过期后重新计算。临时文件与目标同目录，写完并刷新后按平台语义替换。新建使用“目标必须不存在”的提交原语。只支持元数据能保真的普通文本，特殊文件或多硬链接文件默认拒绝。任何失败都报告实际观察到的文件状态。

**执行。** 每次 `run` 显示解析后的程序与逐项参数、工作目录、超时和宿主权限，再由用户批准。默认直接启动可执行文件。即使程序叫作“测试”，它仍可能执行仓库中的任意代码。用白名单构造子进程环境，显式选择工具链所需变量，模型密钥与会话句柄不得继承。stdout/stderr 并行读取，满额后仍继续排空，仅保留有界头尾及字节计数。终端呈现时过滤控制序列。退出码 0 只证明这条命令报告成功，空测试集等情形还须看测试器输出。

**支持边界。** 首版是本机可信项目模式。内置文件工具以工作区根句柄和系统文件标识为依据，逐层处理链接与重解析点。Windows 拒绝替代数据流、设备路径和越界重解析；平台无法证明路径安全时拒绝该操作。用户批准的宿主进程拥有该账户实际可用的文件和网络权限，其输出也可能含别处的数据；批准界面须说明输出摘录将发给模型。若要支持无人值守运行第三方仓库，先交付经过验证的进程隔离、挂载与网络限制，再开放该模式。[Windows 重解析点](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points-and-file-operations) · [Linux 路径解析](https://man7.org/linux/man-pages/man2/openat2.2.html)

Windows 进程后端显式指定程序路径，把结构化参数编码给经验证的目标程序，覆盖空参数、引号、反斜线与 Unicode。先建立受控 Job 再让子进程运行，取消时终止 Job 并收集结束状态。POSIX 后端采用参数数组和进程组，先请求终止，宽限后强制回收。主动脱组的进程不在此保证内。Windows 文件替换有部分失败状态；恢复时检查目标、临时文件和备份，保留可确认的副本。Linux 如需承诺掉电后的目录项持久性，还须同步父目录。[Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) · [Windows 文件替换](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) · [Linux fsync](https://man7.org/linux/man-pages/man2/fsync.2.html)

## 6. 会话存储与崩溃恢复

选择**每会话一个本机 SQLite 数据库**，放在用户私有数据目录，工作区之外。我们确实需要把一条助手消息和 N 个待执行调用一起提交，还要能判断某个调用是否已经派发。用 JSONL 也能做，但要自行定义记录组提交、尾部损坏识别、互斥与升级。这个工作量足以抵消少链接一个库的收益。单写者、短事务、默认回滚日志 `DELETE` 配合 `synchronous=EXTRA` 是首版基线。设备与文件系统须兑现刷新语义；网络共享和同步盘不在首版会话库支持范围。[SQLite 原子提交](https://sqlite.org/atomiccommit.html) · [SQLite 同步等级](https://sqlite.org/pragma.html#pragma_synchronous)

| 最小持久对象 | 需要保留的事实 |
| --- | --- |
| 会话 | 格式版本、会话 ID、工作区根身份、模型与协议配置、用户选择的范围、预算、结束或暂停原因 |
| 消息 | 单调序号、所属任务和轮次、角色、有序内容块。可见助手草稿只活在内存里 |
| 调用 | 本地 ID、所属助手消息、批内位置、提供方调用 ID、规范化参数、授权决定、派发状态、完成结果。编辑另存前后摘要和恢复所需文件名 |
| 证据与请求清单 | 有界的工具输出、诊断与差异、截断信息、请求引用的消息区间、模板和策略版本、尝试号及用量。凭据、全量网络包和无限日志不入库 |

**提交顺序。** ① 用户输入入库。② 一个事务提交完整助手回复及全批调用。③ 对每个待执行动作，批准与复核后持久化“即将派发”，提交成功才允许工作线程触碰外部状态。④ 工作完成后，结果、证据与调用终态一并提交。⑤ 全批结清才允许发下一次模型请求。每会话持有 OS 级独占写者锁；数据库事务之间仍持锁，防止两个 CLI 同时恢复并派发同一调用。锁按会话隔离，另一个会话或编辑器仍可能修改同一工作区。

| 中断位置 | 重开后的可知事实 | 恢复动作 |
| --- | --- | --- |
| 只有用户消息或未完成的模型流 | 没有已提交的工具提案，服务端可能已计费 | 标记该尝试中断。用户继续后用完整任务重建请求 |
| 已有调用，尚无派发标记 | 按提交顺序，该调用尚未触碰外部状态 | 恢复到准备阶段，重新核对目标；写入与命令重新批准 |
| 有派发标记，缺少结果 | 动作可能尚未开始，也可能已部分或全部完成 | 只读操作可重新观察并标明新时间。编辑比较当前内容与预期前后态。命令显示“效果未知”，禁止自动重发 |
| 已提交部分结果 | 哪些调用已结清、哪些尚未开始可以精确区分 | 复用已存结果。若有未知效果，先暂停整批并记其余项跳过 |
| 全批结果已提交，下一请求未完成 | 工具结果已可靠保存 | 直接投影已有结果继续；同一工具不会因网络重试而再运行 |

用户核对未决命令后，可结束任务，或确认“接受效果未知，继续”。宿主保留原结果并把新决定单独入库，再补齐提供方需要的工具结果。重新执行属于一次新的显式动作，分配新 ID 和批准。即使文件现状等于预期后态，也只能证明此刻内容一致。SQLite 事务与宿主进程、编辑器、文件系统之间没有跨资源的恰好一次提交。[SQLite 原子提交的适用范围](https://sqlite.org/atomiccommit.html)

磁盘写满时，派发标记写失败即停止执行。外部动作已结束而结果写失败时，停止后续派发，当前终端报告已观察到的结果及未能保存的原因，重开后按未决动作处理。打开新格式库时只给诊断，不降级覆盖。旧格式先备份，再做事务迁移并校验。默认不上传历史，记录可能包含项目源码；删除会话作用于本地会话库及其关联文件，不能撤回已发出的请求。

恢复时再次核对根目录身份、提供方与当前授权。路径字符串相同而目录已被替换时先暂停。用户收紧读取范围或改变模型目的地后，旧历史也要重新过发送策略；无法从混合消息中可靠剥离被撤回材料时开启新会话。这样可防止旧会话绕过新边界。

## 7. 上下文是下一次请求的视图

同一段 8 MiB 构建输出，对用户有用的可能是第一条编译错误，对模型有用的可能是这条错误及失败的目标，对恢复有用的是退出码、摘录和版本。把三者共用一个无限增长的字符串，最终会同时拖慢界面、塞满窗口、放大隐私暴露。首版按来源保存有界证据，每次请求再构造视图。

**预算公式。** 设模型窗口为 W，输出预留为 O，估算安全余量为 M，固定系统指令、工具 schema 和序列化包装共消耗 F，则历史、当前用户任务与证据可用预算为 **W − O − M − F**。每个块只记账一次。先固定用户原始约束、当前补充、未解决决定及最近完整调用组，再分配旧历史。若硬性保留项本身超限，显示各项占用，请用户分拆任务或缩小输入。限制通过减少旧材料处理，不能静默截掉用户的约束。

1. 先控制源头。读取分页，命令输出保留头尾和真实遗漏量，检索返回路径与行号。为旧证据保留出处、版本和获取时间。未保留的中段明确标为不可取回；可重读文件，重跑命令须另行批准。
2. 最近完整轮次按新到旧装入，再按原顺序序列化。助手的工具提案和整批结果为不可拆单元。历史过大时将旧的完整组替换为宿主生成的事实清单，含用户决定、已改路径、版本变化、失败原因及验证记录的本地序号。清单以带明确来源的普通上下文进入请求。保留原始已存记录。
3. 起步使用保守的本地估算并用实际用量校准。中英文、长代码和 JSON 的误差单独测。接近边界时可对最终序列化内容使用提供方计数接口，其额外请求和延迟单独记账。遇到明确的上下文超限错误，缩减旧历史后最多修复一次。仍超限则停止。[Anthropic Token Counting](https://platform.claude.com/docs/en/build-with-claude/token-counting)
4. 固定顺序与模板版本。给定同一历史快照、模型配置、预算和策略版本，离线能重建相同的逻辑请求及裁剪清单。重开会话或工作区发生变化后，旧观察继续带旧版本标签。恢复编辑时重新获取现状。

**首版接受的损失**是确定性的事实清单可能丢掉较早的设计动机。先用长任务验证这一损失，再决定是否增加模型摘要。引入时把摘要当带来源区间的派生记录，保留重建能力。仓库索引、向量检索和跨项目记忆均要经独立任务集证明能提升正确率，才承担其索引更新与隐私成本。

## 8. C++ 工程形态与最小接口

选用 C++20、CMake Presets、CTest，首批编译器为 MSVC 与 Clang。一个可执行入口加内部静态链接足够表达边界。RAII 管理句柄、临时文件、连接和事务，跨线程传拥有所有权的有界值，借用的缓冲区只能活在当前回调中。枚举与结构体表示取消、失败和未知效果。C 库回调边界捕获异常，清理资源后向控制器返回错误。所有超时用单调时钟，展示与审计另记墙钟。[CMake Presets](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html)

| 选择 | 选择理由与代价 | 何时重新评估 |
| --- | --- | --- |
| libcurl + 平台 TLS | 复用连接、代理、证书校验及跨平台维护。工作者持有 multi handle，用 poll/wakeup 响应取消。固定解析器与 TLS 后端，验证 DNS 阶段也能按时退出。默认 HTTPS、验证主机与证书、禁跨目的地携带凭据 | 第二种传输确有需求，或发布物体积、取消延迟实测超标。[multi 接口](https://curl.se/libcurl/c/libcurl-multi.html) · [wakeup](https://curl.se/libcurl/c/curl_multi_wakeup.html) |
| nlohmann/json，仅出现在协议与存储边界 | 在有界 SSE 事件上先求可读性。限制嵌套、大小及重复字段，避免含糊解析。单独编译适配层，核心头文件不暴露 JSON 类型 | 用同一轨迹证实 JSON 构造、分配或编译时间是瓶颈，再比较 SAX 或替代解析器。[SAX 接口](https://json.nlohmann.me/api/basic_json/sax_parse/) |
| SQLite C API，薄 RAII 包装 | 事务和恢复直接对应产品要求。首版无需 ORM、后台数据库进程或全文索引 | 记录持久提交频率、数据库大小和等待时间，有读写竞争再评估 WAL |
| 系统文件／进程 API，平台已有 SHA-256 实现 | Windows 与 POSIX 的替换、路径、进程和引号规则不同。显式后端能说清保证。摘要用于版本校验，工具链不得自行重造密码学 | 第二平台通过相同契约夹具才纳入发布，元数据保真失败就收窄支持类型 |
| 行式 CLI、延迟初始化 | 安装后即可运行。首次提示前不扫描工作区、不连模型。流式输出按时间窗口合并刷新，非交互模式只使用已授予能力，需要人工批准则以明确状态退出 | 用户确实需要跨屏差异浏览或 IDE 集成，再选择 TUI 库或进程间协议 |

依赖固定版本、构建选项和校验值。建议首版用 vcpkg manifest 加固定 baseline，私有实现目标承担第三方头文件，发行包附许可证及依赖清单。Release 基准同时记录主程序和随附 DLL 大小。依赖升级须通过协议、TLS、恢复和平台夹具。构建期工具与用户机器上的运行时依赖分别统计。

### 接口契约

下表给出操作、所有权和失败语义。内部的投影和权限判定用普通函数实现；需要真实与离线实现互换的 I/O 边界才引入可替换接口。

| 边界 | 输入 → 输出 | 调用者能依赖的行为 |
| --- | --- | --- |
| 会话控制器推进一步 | 用户输入、完成通知或取消 + 当前状态 → 下一动作、持久提交或终态 | 单写者处理事件；开始新动作前先处理已到达的停止请求 |
| 上下文投影 | 已提交历史快照、能力描述、模型规格、预算 → 有序请求视图与取舍清单 | 无 I/O，输入相同则输出相同。返回无法满足的预算项 |
| 模型生成 | 不可变请求、尝试 ID、截止时间、停止信号 → 预览增量，最终为完整回复或带原因的失败 | 每次尝试只有一个终态。预览不能派发工具；凭据、原始 JSON 与 curl 类型留在适配器 |
| 工具准备与判权 | 调用、工作区、已读版本 → 可显示的动作和权限决定 | 准备阶段允许必要的受限读取。返回允许、待批、拒绝或冲突，不启动命令、不修改目标 |
| 工具执行 | 经批准或策略允许的动作、派发凭据、截止时间 → 工具结果 | 实施执行前复核。区分已成功、已失败、被取消及效果未知，保留已观察的部分效果 |
| 会话提交 | 期望序号、助手回复与调用批／派发标记／工具结果 → 新序号或持久化错误 | 同一提交单位全成或全败，旧序号或重复 ID 返回冲突。能查询记录以核对重试 |
| 平台操作 | 已验证的目标、替换计划或进程规格 → 文件及进程事实 | 返回系统错误、实际状态与清理结果。只在此处处理句柄、平台编码和子进程生命周期 |

**扩展成本应落在可命名的位置。** 新增内置工具只增加 schema、准备、执行及契约夹具，复用授权、取消、证据与恢复。第二家模型由适配器处理角色映射、工具 ID、结束条件和计数；若它需要必须回传的原生内容块，则升级消息存储格式并验证迁移。先有两个真实使用者，再考虑抽取共享协议层。发布第三方 C++ 插件 ABI 会锁定内存所有权和版本兼容策略，等确有外部扩展需求时优先评估带版本的进程协议。

## 9. 性能要为哪一段时间负责

把交互延迟拆成用户可感知的几段：启动到可输入、请求准备、网络与模型首字节、首字节到可显示文字、等待工具、提交证据。C++ 对启动、内存、I/O 和本地流处理有控制力，远端推理耗时由提供方决定。一次多余的“再读整个文件”可能比更换 JSON 库贵得多。因此并列报告**本地开销**和**完成一次正确修改的总成本**。

| 指标 | 测量口径与首轮目标 |
| --- | --- |
| 启动与占用 | 参考机、本地 SSD、Release 包、同一终端环境；分别报告首次冷启动与 100 次热启动。热启动到可输入 P95 ≤ 100 ms，空闲私有内存 ≤ 40 MiB。Windows 记录 private bytes，Linux 记录私有驻留页，按平台独立建基线 |
| 流式显示 | 回环服务发送固定大小的 UTF-8 SSE 事件。测到达首个完整可显示文本事件到写入终端的 P95，目标 ≤ 30 ms；另报真实网络首字节时间。重载时合并刷新，完整回复和终态不得丢失 |
| 输出上界 | 夹具向 stdout、stderr 合计写出 100 MiB。每路保留 64 KiB 头尾合计，工具结果记录实际丢弃量。父进程峰值较空闲新增 ≤ 16 MiB，子进程单列。慢终端下仍能排空或按截止时间停止 |
| 中断 | 在模型等待、审批、进程输出洪峰各注入取消。停止派发及 CLI 显示“正在停止”的 P95 ≤ 100 ms；普通测试进程树在 2 秒宽限后升级终止，3 秒内返回清理结果。无法确认清理完成时输出“未知”并暂停 |
| 端到端质量 | 固定模型版本、预算和初始仓库，报告隐藏测试通过数／总数、越出任务范围的文件数、人工补救次数、每个成功任务消耗的 token 和请求数。失败尝试的费用计入总成本 |

以上数字是**工程假设，当前均未实测**。P0 固定一台参考机，记录 CPU、内存、存储、OS、编译器、构建选项及终端输出方式。测量工具和样本随基准保存；冷启动无法稳定清空系统缓存时注明口径。线上模型有随机性，在同样的任务上重复三次，报告原始通过数，避免单次演示或小样本百分比掩盖回归。

**最先做的优化**是按需读文件、复用 HTTP 连接、限制每次保留的数据、合并终端增量，以及按逻辑边界写数据库。默认只留一份有界的完整模型回复，预览队列满时合并刷新或省略中间帧；终态单独可靠投递。记录每类库、队列和证据的峰值后，再判断是否值得引入自定义分配器、零拷贝视图、协程调度器或并行工具池。

资源限制从协议入口生效。首轮测试配置建议单个 SSE 事件上限 1 MiB、整条回复 4 MiB、每批 16 项调用、单个可编辑文本 2 MiB、每次读取送入模型至多 32 KiB。分别按实际解码／解压后的字节数计数，并设 JSON 深度上限。较大的文本可在读取上限内分页，但整文件超出编辑能力时明确报告。超限结果须带资源名、上限和已读量，P1/P3 用边界值和持续输入校准这些数值。

## 10. 开发路线与验收

每个阶段交付一个可从 CLI 或测试入口独立运行的纵向切片。脚本化模型、临时工作区、假时钟与回环服务允许日常验收离线完成；只有供应商兼容和真实任务质量需要在线复核。阶段按依赖顺序推进，日历工期要等 P0 取得人员与机器基线后再定。

| 阶段 | 可独立交付的能力 | 放行条件 |
| --- | --- | --- |
| P0 · 离线内核 | CLI 接收一个问题，脚本化模型请求一次读取，控制器把夹具结果送回模型并结束。先用内存存储 | 从正常结束、半截调用、取消、预算耗尽四条固定轨迹得到精确的状态和派发次数；同一记录重放 100 次一致。建立启动与内存基线 |
| P1 · 真实只读助手 | 首个模型适配器，受限的目录、读取、检索；一问一答能指出代码出处 | 真实服务完成一次检索与回填；离线逐字节切分中文 SSE、模拟 429、流内报错、重复 ID 及断流。完整编辑提案后接半个调用时，整批派发数为零；取消后迟到回调无效 |
| P2 · 可恢复的单文件编辑 | SQLite、独占写者、逐次批准、单文件编辑和重开会话。在临时仓库修改一行，显示对应差异 | 虚拟停点覆盖提交回复前后、派发前后以及替换后至结果落库前。强杀后没有重复写入；旧版本、目标已存在、歧义匹配、空间不足及两个 CLI 竞争均得到明确结论。拒绝修改时文件逐字节相同 |
| P3 · 完整改码闭环 | 覆盖 Windows 进程、双管道与取消。对开头的空配置案例复现失败、修改、运行指定测试、展示证据 | 对同一任务分别演示修复通过、环境缺失、测试仍失败、验证后再次编辑四种结果。输出洪峰和持有管道的子孙进程下仍能退出或标明清理状态。强杀恢复后未决命令的自动重发数为零 |
| P4 · 首个可分发版本 | 长会话裁剪、离线迁移、资源限制、独立安装包、固定任务集质量评测 | 新 Windows 环境无需开发工具即可启动并读取文件；构建任务单列所需项目工具链。超窗口用例保留用户约束和完整调用组。关键路径性能达到第 9 节目标，或在发布说明写明实测偏差并据此收窄支持范围 |

**首版质量门槛。** P0 先冻结 12 个有唯一验收条件的小任务：4 个代码定位、4 个单文件修复、2 个含现有未提交改动的编辑、2 个验证环境异常。每题用隔离的仓库副本，预置允许修改的路径、预期结果及隐藏断言。P4 每题重复三次，初始放行目标为至少 30/36 次正确完成；环境异常题的正确答案是保留已有工作并准确报告缺失证据。另要求所有确定性契约用例通过，未经批准的写入、重复派发未决命令、伪报验证通过三项观测次数均为零。小样本用于发现回归，不能外推为一般仓库成功率。

**测试优先级。** 先测不可逆或难以察觉的错误，再测顺利路径的速度。协议解析用录制的脱敏流和随机切块。文件夹具覆盖含空格与中文的路径、CRLF/BOM、长行、重解析点、外部改写和元数据。进程夹具覆盖参数往返、超时、非零退出、持管道的子孙、双管道洪峰。数据库夹具同时检查磁盘上的工作树和会话记录。离线重放复核当时的决策与证据，不重新执行原命令。

## 11. 已知缺陷与决策触发条件

| 尚未解决的问题 | 首版承担的限制 | 验证方法或改变设计的条件 |
| --- | --- | --- |
| 外部编辑器可在最后一次校验与文件替换之间写入 | 版本复核能拦住已观察到的过期编辑；通用文件替换没有跨进程的比较并交换保证 | 用受控并发写入放大竞态，区分可检测冲突与剩余窗口。多人或敌对并发写入需求成立时，改用隔离工作副本与显式合并 |
| Windows 文件元数据、重解析点和锁的行为复杂 | 首版限定本地普通文件和经验证的替换路径；未知 ACL、加密属性或不支持的文件系统需显式报告 | 在 NTFS 上核对权限、替换失败的现场及原文件可恢复性。未通过的文件类型只读 |
| 宿主执行具备账户权限 | 审批有摩擦，且获批程序能绕开内置文件工具。后台服务、逃离进程组及外部系统效果可能无法核实 | 用真实工作流统计批准次数与放弃率。无人值守或不可信仓库成为目标时，先验证隔离后端的文件、凭据、网络与后代进程边界 |
| 简单编辑与检索可能增加模型往返 | 唯一旧片段容易因重复代码而失败；按需遍历在大仓库可能反复命中扫描上限 | 按任务记录重读次数、匹配失败率和扫描耗时。可分别对比多片段编辑、受限的原生搜索后端或索引，保持相同权限和隐藏测试 |
| 事实清单可能遗漏长期意图 | 长任务的前期权衡可能被裁掉；整个会话数据库也可能持续增长 | 构造必须引用早期决定的长任务，对比正确率、输入 token 与耗时。确有损失再加入可核查的摘要或更细的取证接口 |
| 单提供方可能把协议假设带入核心 | 首个适配器仅覆盖列明的文本与工具子集；切换模型可能丢失专属内容 | 接第二家前用录制样本检验角色、调用 ID、结束条件、专属状态与计数。无法无损续聊时开启新会话并显式转交事实 |
| 线性历史、同步持久化与串行调度限制吞吐 | 高速本地模型或很多独立小读取可能让磁盘同步及串行等待成为主要成本 | 按请求记录同步次数、耗时和可并行比例。只有同一任务集显示端到端收益，才合并提交或增加只读并发，仍保留派发前的持久边界 |

**开工判据。** 第一块可以直接实现的工作是 P0 的离线循环。最有区分度的演示只有两步：正常轨迹中，读取结果确实决定了模型的下一步；将同一回复截在最后一个工具参数中间，工作区副作用立即归零。两者成立后再接真实模型。后续每一层都应让用户更容易核对一次具体修改的来龙去脉。
